MintGuard

An AI agent that only mints what it has verified — built for NEAR HACKATHON 2026: Build Beyond Boundaries.

The problem: an agent asked to mint an NFT today either holds a raw EVM private key (one leak = wallet drained) or blindly trusts whatever contract a post links to (free-mint scams, honeypots and fake “free” mints that drain approvals are routine on BSC).

Track: agents (Agent Economy) Also: security · open NEAR Chain Signatures (MPC) BSC vetting · testnet demo

How it works — in 3 steps

1VET The agent vets any BSC free-mint contract before touching it: Sourcify verification (ABI + source), proxy detection, free-quota reads (totalMinted / remaining / maxSupply), an eth_call simulation of the mint from the agent’s wallet, and a honeypot / tax / owner safety scan. Read-only — it never sends a transaction. Result: a scored verdict, SAFE, RISKY, BLOCK or NOT_MINT.
2SIGN Only on a clean verdict, the mint is executed cross-chain from a NEAR account via NEAR Chain Signatures: the agent’s EVM address is derived from its NEAR account and the BSC transaction is signed by NEAR’s MPC network. No seed or private key ever exists on the agent’s machine.
3RECORD Every vetting and mint is appended to the agent’s reputation ledger, so other agents (and humans) can check what this agent has verified before trusting it.

What each verdict means

VerdictScoreMeaningWhat MintGuard does
SAFE≥ 80 Verified source, no hard-block risk, quota available, simulation passed. May proceed to the policy gate, then SIGN.
RISKY20–79 Something needs a human: simulation reverted, quota unknown or sold out, paid lane, partial match, unrenounced owner… Stops. A human reviews the risks list before anything proceeds.
BLOCK≤ 19 Hard block: unverified source, paused contract, honeypot, or buy/sell tax > 10%. Never mints. No human override in the agent flow.
NOT_MINT0 Not a mint contract at all (no mint/claim function in the ABI). Rejected outright — e.g. WBNB above.

Scoring starts at 100. Paid mint (−25), simulation revert (−30), quota sold out (−40), partial Sourcify match (−10), proxy (−5), tax 6–10% (−25), unrenounced owner (−5). Full rules: docs/vetting-pipeline.md. Known limits: freeQuotaRemaining: null means “unknown”, not “unlimited”; mintPriceWei: null means “no price getter found”.

2 · SIGN — the agent’s EVM address comes from NEAR, not from a key

NEAR Chain Signatures derives one EVM address per (NEAR account, path) with additive key derivation — no mnemonic, no BIP32, no private key anywhere. This derivation was verified offline against the MPC contract’s own derived_public_key view call, on testnet and mainnet. Real output, run 9 Nov 2026:

So example.testnet + path ethereum-1 → 0xD8ebbAA4f6558cc6b322987194Fd663a976272bD. To sign, the agent calls sign on the MPC contract (v1.signer-prod.testnet on testnet, v1.signer on mainnet) with the 32-byte transaction hash; the MPC network returns the ECDSA signature and the agent broadcasts the signed BSC transaction. Cost per sign: 1 yoctoNEAR deposit + ~7 TGas burned (300 TGas prepaid, unused refunded) — measured from the published chainsig.js@1.1.16 bundle; re-measure at build time.

The honest MPC caveat. Chain Signatures removes the single-key failure mode, but it replaces it with a threshold assumption: security holds only while fewer than the threshold of MPC participants are compromised (on-chain state, Oct 2026: 17 participants, threshold 11; the set and threshold are public on the contract and can change by participant vote). MintGuard also recommends a function-call key scoped to sign on the MPC contract only — never a full-access key — so a leaked agent key can at most request signatures for that account’s own derived addresses. See docs/chain-signatures-research.md §9.
